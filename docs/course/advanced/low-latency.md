# 降低延迟与资源占用

同样是 60 FPS，画面可以紧跟输入，也可以播放一段已经排队的旧图像。远程操作更关心最近一帧何时显示，所以需要**同时检查吞吐、帧龄和输入反馈**。

## 当前链路已经采用的措施

| 环节 | 当前实现 | 限制与观察点 |
| --- | --- | --- |
| 原始帧队列 | 出队时优先保留最新可用帧，归还较旧 buffer | `skipped` 记录主动跳帧；只适用于原始帧 |
| 输入内存 | DMA-BUF 导出并映射到编码设备 | 导入失败回退复制，换平台重新核对布局 |
| 硬件编码 | 1080p60、12 Mbps VBR、GOP 60 | 约 8.5 ms 是调用耗时，不是端到端延迟 |
| 本地发送 | 短写重试、整包截止时间、失败重连 | 不能靠无限缓存隐藏慢消费者 |
| RTP 时间 | 使用采集时间戳生成媒体时间 | 进程重连需重建映射与解码参考状态 |
| 解码恢复 | PLI/FIR 请求新的 IDR | 请求限频，不能任意丢弃 P 帧 |
| 浏览器 | 支持时请求低抖动缓冲目标 | 偏好不是强制保证，浏览器仍根据网络调整 |
| 绝对鼠标 | 合并积压位置事件 | 相对位移、滚轮和按键不能按同样规则覆盖 |

在 `kvm_video_demo/main.cpp` 中查找 `capture policy=latest` 和 `VE imported`，在 `kvm/ui/src/utils/interactivePlayout.ts` 中查看浏览器缓冲偏好。配置值为 0 不表示网络和浏览器已经没有缓冲。

## 鼠标跟手感包含两条路径

```text
本地操作 → 网络输入 → HID 报告 → 被控系统处理和绘制
                                        ↓
浏览器显示 ← 解码与网络视频 ← 编码与采集 ← HDMI
```

图 1：输入与视频返回路径。

看见远端光标变化必须等待输入路径和视频返回路径。只缩短 HID 报告处理时间，不一定能消除画面上的全部落后。

**静止后仍然错位，应先检查绝对坐标映射、视频留边和源端桌面配置**；**运动时落后而停止后对齐，再测量链路延迟**。相对鼠标发送的是位移，源系统的加速度和缩放会影响实际像素移动。

## 原始帧和编码帧不能用同一种丢弃策略

原始图像相互独立，跳过旧原始帧可以避免处理过期画面。H.264 P 帧可能引用前面的图像；随意删去一帧再继续发送，接收端可能花屏直到新的 IDR。

因此发生传输中断后，应重新同步参数集并请求关键帧，而不是只让接收端忽略解码错误。通过增加队列换来“没有丢帧”，也可能付出越来越大的交互延迟。

## 哪些结果还需要单独测量

当前固定码率配置尚未形成网络反馈驱动的动态编码码率调整。Wi-Fi 波动、带宽受限和远距离访问需要分别测试，不能把局域网短测推广为所有网络保证。

后续测量记录输入到 USB 驱动、源设备实际处理、视频返回和浏览器呈现的时间。**跨设备时间戳须先解决时钟对齐**；高帧率外部录像可作为另一种观测方式。完整方法和样本尚未形成之前，不在参数表中填写猜测的总延迟。

本章的产物是一张分段测量表，以及一次保持输入条件一致的对照实验。优化是否成立，由帧龄、画质、资源与异常恢复共同判断。
